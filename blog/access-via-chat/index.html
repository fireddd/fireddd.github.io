We stopped making engineers wait for access

Role management via chat: an agent I built that makes non-production access self-serve, audited, and locked out of production.

  • AI agents
  • Slack
  • Access management
  • Least privilege
  • In trial

Getting a role usually means raising a request with another team and waiting for them to get to it. I built an AI agent that takes those requests in plain language in Slack and applies them itself.

Roles and permissions, from zero

  • Tenant. One customer's own space on a shared platform, with its own data, users and settings.
  • Permission. A single action, such as viewing a report or inviting a user.
  • Role. A named bundle of permissions, such as "admin" or "view-only".
  • Granting. Giving a user a role in a specific product and tenant.

Granting is guarded for two reasons. Least privilege: give each person the smallest role that does the job. Environments: production is what customers use, and non-production copies are where teams build, test and demo, so a mistake there costs minutes rather than a customer.

The problem

People across the company need roles all the time, to reproduce a bug or demo a feature, and they can't grant one to themselves. Only the platform team can. So they raised a request with the platform team's on-call and waited in that queue, often for a role that turned out to be the wrong one, or for the first of several personas they needed.

Both sides lost: the teams asking lost time waiting, and the on-call spent theirs on repetitive, low-risk requests instead of platform work.

The idea: just ask

The agent handles these requests in plain language in Slack. There is no form, no ticket and no new tool to learn, and you can ask for yourself or for a teammate. These are the kinds of requests people made during the trial:

  • "Give a teammate admin access to one of our apps for a tenant."
  • "Make a user a marketing user for workflows."
  • "Give a user view-only access."
  • "For this environment, what are my roles for this tenant?"

What it can do

  • Roles. It sets, changes or removes a user's role in a product, and maps loose wording like "admin" or "view only" to the tenant's real role.
  • Invites. It invites a new user with a role, or re-sends an expired invite, once you confirm.
  • Enabling users. It reactivates a disabled user without changing their role.
  • Staff access. It grants internal staff access, or time-boxed edit access within a tenant.
  • Look-ups. It shows which roles someone holds, which roles a tenant offers, and licence totals and usage.
  • Bulk requests. It handles "view-only for all apps" by picking the lowest-privilege role in each app the tenant has, then lists exactly what it assigned.
  • Self-description. It explains what it can do when you aren't sure what to ask.

How a request flows

  1. You ask in Slack.
  2. The agent finds the tenant.
  3. It matches your wording to the tenant's real roles.
  4. It validates the request.
  5. It applies the change.
  6. It reports the result for each user.

A clear request just runs. The agent asks one short question only when something is missing or ambiguous, and it never guesses a role or an email address. If you don't name an environment, it uses the safer non-production one and tells you so.

Designing for safety first

Letting an AI agent change access sounds risky, so the guardrails were the main design work:

  • Non-production only. Production requests are declined, and the services behind the agent reject production calls by design, so it can't reach production even by mistake.
  • No guessing. It never infers an email address from a name or picks between ambiguous roles; it asks instead.
  • Allow-listed domains. Only approved email domains can be invited or changed.
  • No lock-outs. It blocks any removal that would leave a user with no role.
  • Least privilege. It declines the highest-privilege role and offers the next level down, and it hands removal of staff access to IT or the platform team.
  • Honest reporting. It reports an invite as "invited, must accept", never as "access granted", and re-reads the user's state after every change to report what they hold now.
  • No blind retries. It never retries a write automatically, and it serialises concurrent changes to the same tenant.
  • Audit trail. It logs every change with the requester's identity.
  • Protected attributes. It cannot set sensitive flags through the role and invite paths.

How it's built

The agent is a thin skill on top of a small set of internal, non-production endpoints. The skill does the validation, so users never touch the APIs directly.

Some changes touch two systems: our app and our identity provider. The agent keeps them in step, and if the sync fails, it restores the previous value.

I tested it with unit tests, evals for the agent skill, and end-to-end runs against a real identity provider in a non-production project.

What's next

The agent is in trial. These items are planned and not built yet:

  • Granular permissions. Permissions per action, with clear denials and audit logging.
  • A fuller test plan. End-to-end coverage of the happy paths and the key failure scenarios.

The point stays the same: access to non-production environments shouldn't mean waiting. With the agent it is self-serve and audited, and it is locked out of production.
