Agents · Access management

We stopped making people wait for access

Role management via chat: a skill I built for our internal AI assistant that makes non-production access self-serve, audited, and locked out of production.

  • AI agents
  • Slack
  • Access management
  • Least privilege
  • In use

The problem

People across the firm need roles all the time, to reproduce a bug or demo a feature, and they can't grant one to themselves. Only the platform team, my team, can. So they raised a request with our on-call, or with someone they knew on the team, and waited, often for a role that turned out to be the wrong one, or for the first of several personas they needed.

Both sides lost: the teams asking lost time waiting, and our on-call spent theirs on repetitive, low-risk requests instead of focusing on their core responsibilities.

For non-production environments, none of that queueing should be necessary. Nothing there touches a customer; you just want to get your work done. That is why I built a skill for our internal AI assistant that grants non-production roles from a plain-language request in Slack, with no queue.

Roles and permissions, from zero

  • Tenant. One customer's own space on a shared platform, with its own data, users and settings.
  • Permission. A single action, such as viewing a report or inviting a user.
  • Role. A named bundle of permissions, such as "admin" or "view-only".
  • Granting. Giving a user a role in a specific product and tenant.

What already existed

I didn't start from scratch. Three things were already in place:

  • Orca. Our internal AI assistant, built and maintained by another team. It already lived in Slack, and it spins up an AI coding agent to do the work and manages that agent's lifecycle.
  • Skills. Orca's way of learning new jobs. A team registers a skill with a description of the requests it should handle, and the agent picks it up when a request matches.
  • Our app and identity provider. The systems where users and their roles actually live, which only our tooling on the platform team could change.

What was missing was a way for anyone to get a role without going through us. That is the part I built: a skill for the platform team's access use case, added to Orca, and the plumbing behind it.

The idea: just ask

The agent handles these requests in plain language in Slack. There is no form, no ticket and no new tool to learn, and you can ask for yourself or for a teammate. These are the kinds of requests people make:

  • "Give a teammate admin access to one of our apps for a tenant."
  • "Make a user a marketing user for workflows."
  • "Give a user view-only access."
  • "For this environment, what are my roles for this tenant?"

How a request flows

A clear request just runs. If you don't name an environment, the agent uses the safer non-production one and tells you so.

Designing for safety first

Letting an AI agent change access sounds risky, so the guardrails were the main design work:

GuardrailWhat it means
Non-production onlyDeclines any request for a production environment.
Validation firstChecks every request before it makes it.
No guessingNever infers an email address from a name or picks between ambiguous roles; it asks you in Slack instead.
Allow-listed domainsInvites or changes only users on approved email domains.
No lock-outsBlocks any removal that would leave a user with no role.
Least privilegeDeclines the highest-privilege role and offers the next level down, and it hands removal of staff access to IT or the platform team.
Honest reportingReports an invite as "invited, must accept", never as "access granted", and re-reads the user's state after every change to report what they hold now.
No blind retriesNever retries a write automatically, and it serialises concurrent changes to the same tenant.
Audit trailLogs every change with the requester's identity.
Protected attributesCannot set sensitive flags through the role and invite paths.

Where the safety lives

The guardrails above are what the agent does. These are what make them hold even if the agent gets something wrong:

  1. Production is blocked in the services. Every API exposed for the skill is guarded by permissions so that it works only with non-production environments, so no wording of a request can get past it.
  2. New APIs wrap the existing ones. The APIs exposed for the skill are wrappers on top of the existing ones, so every existing check and nuance still runs, such as writing to the third-party auth service.
  3. Users never touch the APIs. Every call goes through the skill.
  4. Two systems stay in step. Some changes touch both our app and our identity provider; if the sync fails, the previous value is restored.

How we test that it triggers

The skill only helps if the agent picks it up for access requests and leaves it alone for everything else. We have evals that test exactly that:

  1. A labelled set of requests. The skill ships with example requests, each marked as one that should trigger it or one that shouldn't, and a lint step requires a minimum number of both.
  2. Several runs per request. Each request goes to the agent more than once, because the same prompt doesn't always lead to the same choice.
  3. Triggered or not. A run counts as triggered if the agent calls the skill or reads its files.
  4. A pass mark. Each request and the skill as a whole are scored against the rules in the table below.
  5. Run on every change. The evals run on every pull request that touches the skill, with results posted on the PR, and again every week, with results posted to Slack.
CheckPasses when
A should-trigger requestTriggers the skill in at least half its runs.

Where it is now

Folks have started using it. Requests now rarely reach us, and when one does, we trigger the agent to handle it with this skill.

The point stays the same: access to non-production environments shouldn't mean waiting. With the skill it is self-serve and audited.
