Agents · Access management

We stopped making people wait for access

Role management via chat: a skill I built for our internal AI assistant that makes non-production access self-serve, audited, and locked out of production.

  • AI agents
  • Slack
  • Access management
  • Least privilege
  • In use

The problem

People across the firm need roles all the time, to reproduce a bug or demo a feature, and they can't grant one to themselves. Only the platform team, my team, can. So they raised a request with our on-call, or with someone they knew on the team, and waited, often for a role that turned out to be the wrong one, or for the first of several personas they needed.

Both sides lost: the teams asking lost time waiting, and our on-call spent theirs on repetitive, low-risk requests instead of focusing on their core responsibilities.

For non-production environments, none of that queueing should be necessary. Nothing there touches a customer; you just want to get your work done. That is why I built a skill for our internal AI assistant that grants non-production roles from a plain-language request in Slack, with no queue.

Roles and permissions, from zero

  • Tenant. One customer's own space on a shared platform, with its own data, users and settings.
  • Permission. A single action, such as viewing a report or inviting a user.
  • Role. A named bundle of permissions, such as "admin" or "view-only".
  • Granting. Giving a user a role in a specific product and tenant.

What already existed

I didn't start from scratch. Two things were already in place:

  • Blue Whale 🐋. Our internal AI assistant, built and maintained by another team. It already lived in Slack, and it spins up an AI coding agent to do the work and manages that agent's lifecycle.
  • Our app and identity provider. The systems where users and their roles actually live, which only our tooling on the platform team could change.

What was missing was a way for anyone to get a role without going through us. That is the part I built: a skill for the platform team's access use case, added to Blue Whale, and the plumbing behind it.

The idea: just ask

The agent handles these requests in plain language in Slack. There is no form, no ticket and no new tool to learn, and you can ask for yourself or for a teammate. These are the kinds of requests people make:

  • "Give a teammate admin access to one of our apps for a tenant."
  • "Make a user a marketing user for workflows."
  • "Give a user view-only access."
  • "For this environment, what are my roles for this tenant?"

How a request flows

A clear request just runs. If you don't name an environment, the agent uses the safer non-production one and tells you so.

Designing for safety first

Letting an AI agent change access sounds risky, so the guardrails were the main design work:

GuardrailWhat it means
Non-production onlyDeclines any request for a production environment and points you to the on-call.
All or nothingDeclines the whole request if any part of it is out of bounds, rather than quietly doing the safe half.
Validation firstChecks every request before it makes it, and the code checks it again before anything goes over the network.
No guessingNever infers an email address from a name or picks between ambiguous roles; it asks you in Slack instead.
Allow-listed domainsInvites or changes only users on approved email domains.
No lock-outsBlocks any removal that would leave a user with no role, and when swapping a role, adds the new one before removing the old.
Least privilegeDeclines the highest-privilege role and offers the next level down, and it hands removal of staff access to IT or to us.
Honest reportingReports an invite as "invited, must accept", never as "access granted", and re-reads the user's state after every change to report what they hold now.
No blind retriesNever retries a write automatically; if a write times out, re-reads the user to see whether it landed. It also serialises concurrent changes to the same tenant.
Audit trailLogs every change with the requester's identity.
Protected attributesCannot set sensitive flags through the role and invite paths.

How it's built

What the skill is made of

PartWhat it does
TriggerMatches any request for a role change or access, so the agent picks the skill up from plain language.
SKILL.mdLists every capability the skill exposes, as commands the coding agent can run.
Access.mdWrites down the nuances of every use case, so the agent never has to guess them.
Deterministic codeHolds everything deterministic as ordinary code, exposed to the agent through clients, helpers and the like: role matching, least-privilege ranking, validation, the API calls, and turning each response into a clear outcome.

Where the safety lives

The guardrails above are what the agent does. These are what make them hold even if the agent gets something wrong:

  1. Production is blocked in the services. Every API exposed for the skill is guarded by permissions so that it works only with non-production environments, so no wording of a request can get past it.
  2. New APIs wrap the existing ones. The APIs exposed for the skill are wrappers on top of the existing ones, so every existing check and nuance still runs, such as writing to the third-party auth service.
  3. Users never touch the APIs. Every call goes through the skill.
  4. Two systems stay in step. Some changes touch both our app and our identity provider; if the sync fails, the previous value is restored.

How we test it

Two kinds of evals run against the skill:

EvalWhat it checks
TriggerWhether the agent picks up the skill for access requests and leaves it alone for everything else.
DecisionWhether, once it has the skill, the agent makes the right call at each step.

Trigger evals. The skill ships with positive and negative scenarios. Access requests are the positive ones and should trigger it; ordinary requests are the negative ones and shouldn't.

ScenarioExample requestExpected
Positive"Give my teammate view-only access to this tenant."The skill triggers.
Negative"Why is this build failing?"The skill stays out of it.

Decision evals. Trigger evals show that the skill gets picked up; decision evals show what the agent does with it. Letting it run real commands in a test would change real access, so it doesn't run any. Instead, each test puts the agent in a situation and checks what it decides to do next.

  1. Set up a situation. Each case is a request. For a step in the middle of a flow, it also includes what the earlier steps would have returned, so the agent can pick up from there.
  2. Ask for the decision only. The agent answers with what it would do next, without running anything.
  3. Judge the answer. A second LLM, acting as the judge, checks the answer against the decisions we expect and marks each one passed or failed, with the evidence for its call.
  4. Compare with and without the skill. Each case runs once with the skill and once without, and the gap between the two shows what the skill adds.
ScenarioSituationExpected decision
PositiveA clear request, and the tenant's role list has exactly one matching role.Makes the change with that role, without stopping to ask.
NegativeA request for access in production.Declines it, points to the on-call, and runs nothing.

Workflows. Both evals run automatically: on every pull request that changes a skill, with the results posted as one PR comment that updates on each run, and every Monday for all skills, with the results posted to Slack.

Where it is now

People have started using it. Requests now rarely reach us, and when one does, we trigger the agent to handle it with this skill.

The point stays the same: access to non-production environments shouldn't mean waiting. With the skill it is self-serve and audited.
